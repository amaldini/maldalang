17. Actors

MALDA provides native support for the Actor model of concurrent programming. Actors are independent, isolated units of computation that communicate exclusively through asynchronous message passing. Each actor has its own isolated state and processes messages sequentially, ensuring thread-safe concurrent programming without explicit locking mechanisms.

17.1 Actor Declaration

Actors are declared using the actor keyword, similar to class declarations:

actor ActorName {
    // Fields (state)
    var field1 = initialValue;
    var field2;
    
    // Constructor (optional)
    function ActorName(param1, param2) {
        field1 = param1;
        field2 = param2;
    }
    
    // Message handlers
    on messageHandler1() {
        // Handle message
    }
    
    on messageHandler2(param) {
        // Handle message with parameter
    }
    
    // Default handler (optional)
    on handle(msg) {
        // Handles any message that doesn't match a specific handler
    }
}

Actor Components

  • Fields: Actor state variables (isolated per instance)
  • Constructor: Optional initialization function (same name as actor)
  • Message Handlers: Functions declared with on keyword that process incoming messages
  • Default Handler: A handler named handle that receives messages when no specific handler matches

17.2 Spawning Actors

Actors are instantiated using the spawn expression:

var actorRef = spawn ActorName(arg1, arg2);

The spawn expression:

  • Creates a new actor instance with isolated state
  • Starts the actor's message processing loop in a separate task
  • Returns an ActorReference that can be used to send messages
  • Optionally accepts constructor arguments

Example

actor Counter {
    var count = 0;
    
    on increment() {
        count = count + 1;
    }
    
    on get() {
        print(count);
    }
}

var counter = spawn Counter();

17.3 Sending Messages

Messages are sent to actors using the send statement with call-style syntax:

// Call-style syntax
send actorRef.handlerName(arg1, arg2);

// Call-style with callback
send actorRef.handlerName(arg1) then (result) {
    // Handle reply value
};

Message Sending Syntax

  • send target.handlerName(arg1, arg2, ...); - Sends a single message to the given handler with positional arguments
  • send target(arg1, arg2, ...); - Sends a message without specifying a handler name. The message will be routed to the handle handler (if defined), or use handler resolution rules based on the payload
  • send target.handlerName(args...) then (result) { ... }; - Sends a message and registers a callback to run when the reply is received
  • send target(args...) then (result) { ... }; - Sends a message without handler name and registers a callback
  • send target.handlerName(args...) then (result) { ... } timeout milliseconds; - Sends a message with callback and timeout (timeout fires if no reply received)
  • send target.handlerName(args...) then (result) { ... } timeout milliseconds catch (error) { ... }; - Sends a message with callback, timeout, and error handler for timeout cases
  • The call-style syntax sends exactly one message that contains both the handler name (if specified) and all arguments

Example

actor Greeter {
    var name;
    
    function Greeter(actorName) {
        name = actorName;
    }
    
    on greet() {
        print($"Hello from {name}!");
    }
    
    on greetWith(message) {
        print($"{name}: {message}");
    }
}

var greeter = spawn Greeter("Alice");
send greeter.greet();                       // Calls greet() handler
send greeter.greetWith("Hello, World!");    // Calls greetWith() handler with message
send greeter("Hello!");                    // Calls handle() handler (if defined)

Message Passing Details

  • Messages are sent asynchronously (non-blocking)
  • Messages are queued in the actor's mailbox
  • Actors process messages sequentially (one at a time)
  • Multiple actors can send messages to the same actor concurrently

Request/Response with Callbacks

You can send a message and register a callback that will be executed when the receiver replies:

actor Worker {
    on compute(value) {
        var result = value * 2;
        reply(result);  // Sends a reply back to the sender
    }
}

actor Coordinator {
    on start() {
        var worker = spawn Worker();

        send worker.compute(21) then (result) {
            print($"Coordinator: received result = {result}");
        };
    }
}

var coordinator = spawn Coordinator();

// Small delay to ensure actor loop has started
sleep(100);

send coordinator.start();

// Give actors time to process messages and callbacks
sleep(500);
  • reply(value) can only be called inside an actor message handler and when there is a sender to reply to
  • The runtime automatically correlates the reply with the original send ... then (...) { ... } call
  • The callback runs in the sender actor's context, with self referring to the sender

17.4 Message Handlers

Message handlers are functions that process incoming messages. They are declared with the on keyword:

actor MyActor {
    // Handler with no parameters
    on handlerName() {
        // Process message
    }
    
    // Handler with parameters
    on handlerWithParams(param1, param2) {
        // Process message with parameters
    }
    
    // Default handler (receives any unmatched message)
    on handle(msg) {
        // Process any message
    }
}

Handler Resolution

When a message is sent, the runtime determines which handler to call using the following rules:

  1. If an explicit handler name is provided (via send target.handlerName(...)), that handler name is used
  2. Otherwise, if the message payload is a string, it's used as the handler name
  3. Otherwise, the handle handler is used as the default
  4. The runtime looks for a handler with that name
  5. If no specific handler is found, the handle handler is used as a fallback (if defined)
  6. If no handler is found, a runtime error is thrown

Examples:

actor MyActor {
    on handle(msg) {
        print("Default handler: " + msg);
    }
    
    on process(data) {
        print("Process handler: " + data);
    }
}

var actor = spawn MyActor();

// Explicit handler name - calls process()
send actor.process(123);

// No handler name, non-string payload - calls handle()
send actor(456);

// No handler name, string payload - uses string as handler name, calls process()
send actor("process");

Handler Parameters

  • The first parameter receives the message payload
  • Additional parameters can be sent by passing multiple values in sequence
  • Handlers can access actor fields and call other handlers

17.5 Actor State Isolation

Each actor instance has completely isolated state. Fields declared in an actor are private to that instance:

actor BankAccount {
    var balance = 0;
    var accountName;
    
    function BankAccount(name) {
        accountName = name;
    }
    
    on deposit(amount) {
        balance = balance + amount;
    }
    
    on withdraw(amount) {
        if (balance >= amount) {
            balance = balance - amount;
        }
    }
}

// Each instance has its own isolated state
var account1 = spawn BankAccount("Alice");
var account2 = spawn BankAccount("Bob");

send account1.deposit(100);  // account1.balance = 100
send account2.deposit(200);  // account2.balance = 200 (independent)

17.6 Self Reference

Within an actor's message handlers, the self keyword provides a reference to the current actor instance:

actor PingPong {
    var partner;
    
    on setPartner(other) {
        partner = other;
    }
    
    on ping() {
        print("Received ping");
        if (partner != null) {
            send partner.pong(self);  // Send self reference
        }
    }
    
    on pong(sender) {
        print("Received pong");
        if (sender != null) {
            send sender.ping();
        }
    }
}

var ping = spawn PingPong();
var pong = spawn PingPong();

send ping.setPartner(pong);
send pong.setPartner(ping);

Self Reference Usage

  • self can only be used within actor message handlers
  • self returns an ActorReference to the current actor
  • Useful for actors to send messages to themselves or pass their reference to other actors

17.7 Receiving Messages

Within an actor message handler, you can use the receive() function to wait for and retrieve the next message from the actor's mailbox. However, for most use cases, it's recommended to use call-style messaging with callbacks instead:

actor Echo {
    on echo(msg) {
        var received = receive();
        print($"Echo received: {received}");
    }
}

var echo = spawn Echo();
send echo.echo("hello");  // Pass message as argument

Receive Function Details

  • receive() can only be called within an actor message handler
  • receive() blocks until a message arrives in the actor's mailbox
  • For most use cases, prefer call-style messaging with callbacks using send target.handler(args) then (result) { ... } and reply()

Actor Message Declarations (Actor Sugar)

For more structured, protocol-style actors, you can declare messages explicitly inside the actor body using the message keyword and handle them with a receive() + match loop inside a handler:

actor Counter {
    message Inc(amount);
    message Get() -> int;
    var value = 0;

    on start() {
        var running = true;
        while (running) {
            var msg = receive();
            match msg {
                case Inc(n): value = value + n;
                case Get(): reply(value);
                case ""stop"": running = false;
                default: {};
            }
        }
    }
}

var c = spawn Counter();
send c.start();
send c.Inc(1);
send c.Inc(2);
send c.Get() then (result) {
    print($"Result: {result}");  // Prints: Result: 3
};
send c("stop");
  • message Inc(amount); and message Get() -> int; declare the message shapes that the actor expects.
  • Messages can be sent using either send actor.MessageName(args...) or by sending a value that encodes the message (e.g. via a sum type) and matching on it after receive().
  • Inside the loop, match can use variant patterns (e.g. case Inc(n):) and literal patterns (e.g. case ""stop"":).
  • The reply(value) built-in works in receive()-based handlers, allowing message declarations with return types to participate in request/response protocols.
  • Message declarations are optional; they document the actor protocol and pair naturally with pattern matching on values returned from receive().
  • No sleep() needed in the loop: Since receive() blocks until a message arrives, the while loop will automatically wait for messages without consuming CPU. The loop only continues when a message is received and processed.

17.8 Message Passing Between Actors

Actors can send messages to each other, enabling complex communication patterns:

actor Sender {
    on start(receiver) {
        print("Sender: Starting...");
        send receiver.hello();
        send receiver.world();
    }
}

actor Receiver {
    var messageCount = 0;
    
    on hello() {
        messageCount = messageCount + 1;
        print($"Receiver: Received 'hello' (total: {messageCount})");
    }
    
    on world() {
        messageCount = messageCount + 1;
        print($"Receiver: Received 'world' (total: {messageCount})");
    }
}

var receiver = spawn Receiver();
var sender = spawn Sender();

send sender.start(receiver);  // Pass receiver reference

17.9 Concurrent Processing

Actors process messages concurrently. Multiple actors can run simultaneously, and each actor processes its messages sequentially:

actor Worker {
    var workerId;
    var taskCount = 0;
    
    function Worker(id) {
        workerId = id;
    }
    
    on processTask(task) {
        taskCount = taskCount + 1;
        print($"Worker {workerId}: Processed task {task} (total: {taskCount})");
    }
}

// Create multiple workers
var workers = [];
for (var i = 0; i < 5; i = i + 1) {
    workers.append(spawn Worker(i + 1));
}

// Small delay to ensure actor loops have started
sleep(100);

// Send tasks to all workers concurrently
for (var i = 0; i < 10; i = i + 1) {
    for (var j = 0; j < workers.length; j = j + 1) {
        send workers[j].processTask(i);
    }
}

// Give workers time to process all tasks
sleep(500);

17.10 Actor Lifecycle

Actor Creation

  • Actors are created with spawn ActorName(args)
  • Constructor is called during initialization
  • Actor starts processing messages immediately

Actor Execution

  • Each actor runs in its own task/thread
  • Actors process messages from their mailbox sequentially
  • Messages are queued if the actor is busy processing

Actor Termination

  • Actors continue running until the program terminates
  • Actors can be stopped programmatically using the stop() method
  • Actors can stop themselves by calling self.stop() in a message handler
  • When stopped, actors finish processing current message and exit

Stopping an Actor Externally

To stop an actor from outside, call the stop() method on the actor reference:

var actor = spawn MyActor();
// ... use the actor ...
actor.stop();  // Stop the actor externally

Stopping an Actor via Message

Actors can also stop themselves by handling a stop message. This is useful when the actor needs to perform cleanup or make decisions before stopping:

actor Worker {
    var isRunning = true;
    var workCount = 0;
    
    on doWork() {
        if (isRunning) {
            workCount = workCount + 1;
            print($"Worker: Completed work #{workCount}");
        }
    }
    
    on stop() {
        print("Worker: Received stop message, shutting down...");
        // Perform any cleanup here
        isRunning = false;
        self.stop();  // Actor stops itself
    }
}

var worker = spawn Worker();
send worker.doWork();
send worker.stop();  // Send stop message

Note: After calling stop() (either externally or via self.stop()), the actor will finish processing its current message (if any) and then exit. Any messages sent to the actor after it has been stopped will be lost.

17.11 Actor Features Summary

Key Features

  • ✅ Isolated State: Each actor instance has its own isolated state
  • ✅ Sequential Processing: Messages processed one at a time per actor
  • ✅ Asynchronous Messaging: Non-blocking message sending
  • ✅ Concurrent Execution: Multiple actors run concurrently
  • ✅ Self Reference: self keyword for actor self-reference
  • ✅ Message Handlers: on keyword for defining message handlers
  • ✅ Default Handler: handle handler for unmatched messages
  • ✅ Receive Function: receive() to wait for messages within handlers
  • ✅ Request/Response: send ... then (result) { ... } with reply() for callbacks
  • ✅ Lifecycle Management: stop() and self.stop() for actor termination
  • ✅ Type Safety: Actor references are strongly typed

Interpreter and Transpiled Mode Parity

Actor features are supported in interpreter mode, C# transpiled mode, and JavaScript backend mode (local runtime):

  • ✅ Actor declaration, spawning, and message sending
  • ✅ Call-style send target.handler(args) message sending
  • ✅ Call-style sends with callbacks: send target.handler(args) then (result) { ... }
  • ✅ Message timeouts: send ... then (...) { ... } timeout ms catch (error) { ... }
  • ✅ reply() function for responding to callbacks
  • ✅ receive() function for waiting on messages
  • ✅ self keyword for actor self-reference
  • ✅ stop() and self.stop() for actor lifecycle management
  • ✅ Error handling: Invalid usage (e.g., using self outside handlers) throws consistent errors in both modes

When compiling with --mode transpile, actor code is transpiled to C# and uses the same runtime semantics as the interpreter. When compiling with --mode js, actor code runs on the local JavaScript actor runtime and preserves the same core semantics for mailbox ordering, callbacks, timeouts, receive(), and stop behavior.

Current boundary: JavaScript actors are local to the JavaScript runtime process; seamless browser-to-server actor communication is not enabled by default in this phase.

Use Cases

  • Concurrent processing without explicit locking
  • Stateful services with isolated state
  • Message-passing architectures
  • Worker pools and task distribution
  • Event-driven systems
  • Distributed system simulation

Complete Example

actor Counter {
    var count = 0;
    
    on increment() {
        count = count + 1;
        print($"Count: {count}");
    }
    
    on decrement() {
        count = count - 1;
        print($"Count: {count}");
    }
    
    on reset() {
        count = 0;
        print("Counter reset");
    }
    
    on get() {
        return count;
    }
}

// Spawn and use
var counter = spawn Counter();
send counter.increment();
send counter.increment();
send counter.increment();
send counter.decrement();
send counter.reset();

// Give actor time to process messages (important in transpiled mode)
sleep(500);

Note: When using actors in transpiled mode (compiled executables), it's recommended to add a small delay after spawning actors and at the end of programs to ensure messages are processed before the program exits. Use sleep(100) after spawning actors and sleep(500) at the end of programs that use actors.

17.12 Using Actors with Agents

Actors and agents work well together. While agents are classes designed for synchronous AI interactions, storing agents in actor state enables concurrent processing and isolated agent sessions. This is particularly useful for:

  • Concurrent Agent Processing: Spawn multiple actor instances, each with its own agent, to process tasks in parallel
  • State Isolation: Each actor maintains its own agent instance and conversation history
  • Long-Running Sessions: Actors can maintain agent state across multiple message interactions
  • Message-Based Coordination: Coordinate multiple agents through actor message passing

Example:

actor AIAssistant {
    var agent;
    
    function AIAssistant(client) {
        agent = new Agent("Assistant", "helper", "You help users.", client);
    }
    
    on ask(question) {
        var response = agent.think(question);
        print(response.content);
    }
}

var client = new OpenRouterClient();
var assistant = spawn AIAssistant(client);
send assistant.ask("What is MALDA?");

For detailed information about combining agents and actors, including patterns for concurrent agent processing and multi-agent orchestration, see Using Agents with Actors in the Agent Orchestration chapter.
