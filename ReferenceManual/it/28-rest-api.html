28. Server REST API

MALDA include il supporto nativo per REST API JSON-first. Decora le funzioni con i metodi HTTP e ospitale su RestServer (standalone) oppure monta quel server su HttpServer per un'app full-stack a una sola porta.

Parti da qui: Questo capitolo è il riferimento API-first. Hosting delle pagine, @PAGE, HTTPS, file statici, upload multipart e SSE stanno in 26. HttpServer e generazione UI HTML. Chiamare API da MALDA è 29. Client REST Web. Gli helper JWT, CSRF e password sono in 13. Funzioni built-in.

28.2 Sintassi dei decoratori

Le funzioni decorate con un metodo HTTP diventano endpoint REST quando un RestServer parte (o viene montato):

@GET("/api/users")
function getUsers() {
    return parseJSON("[{\"id\": 1, \"name\": \"Alice\"}]");
}

@POST("/api/users")
function createUser(body) {
    var jsonStr = "{\"id\": 3, \"name\": \"" + body.name + "\"}";
    return parseJSON(jsonStr);
}

28.2.1 Metodi HTTP supportati

  • @GET(path) - Gestisce le richieste GET. HEAD corrisponde alla stessa route; il body viene omesso.
  • @POST(path) - Gestisce le richieste POST
  • @PUT(path) - Gestisce le richieste PUT
  • @DELETE(path) - Gestisce le richieste DELETE
  • @PATCH(path) - Gestisce le richieste PATCH
  • @OPTIONS(path) - Gestisce le richieste OPTIONS (il preflight CORS è gestito a parte quando CORS è abilitato)

Coppie method+path duplicate generano un errore allo startup. Usa getRoutes() per ispezionare la tabella registrata.

28.2.2 Decoratori di metadati delle route

I decoratori di metadati opzionali vengono applicati prima della registrazione della route. I prefissi si compongono come group + version + path.

  • @RouteGroup(prefix) / @Group(prefix) / @Prefix(prefix) - antepone un prefisso di gruppo
  • @Version(version) / @ApiVersion(version) - antepone un segmento di versione
  • @Use("middlewareName") / @Middleware("middlewareName") - middleware a livello di route per nome di funzione (una stringa, non una funzione inline)
  • @Validate(schema) - schema di validazione della richiesta (oggetto o stringa JSON)
@RouteGroup("/api")
@Version("v1")
@Use("requireAuth")
@GET("/users/{id}")
function getUserById(id, req, res) {
    return res.json(parseJSON("{\"id\":\"" + id + "\"}"));
}

28.3 Classe RestServer

28.3.1 Costruttore

var server = new RestServer(port);
// OR
var server = new RestServer(port, host);  // host: "localhost" or "0.0.0.0"
// OR
var api = new RestServer();               // port 0: deferred / mounted

port deve essere 0 (deferred/mounted) oppure un intero in 1-65535. Le porte privilegiate (1-1023) sono ammesse; il bind può comunque richiedere permessi elevati o reservation URL del sistema operativo. L'host di default è localhost. Passa 0.0.0.0 per ascoltare su tutte le interfacce. A differenza di HttpServer, non c'è un metodo setHost né l'override MALDA_HTTP_HOST.

28.3.2 Proprietà

ProprietàTipoNote
portintPorta configurata; 0 se deferred/mounted
isRunningboolListener standalone, oppure specchia l'host dopo il mount

28.3.4 Cosa RestServer non ospita

Uno RestServer standalone è solo API. Queste cose stanno su HttpServer (capitolo 26): HTTPS / enableHttps, setHost / MALDA_HTTP_HOST, file statici, @PAGE / @AIPAGE, upload multipart/form-data e SSE ({"sse": true}). Le parti condivise sono req / res / req.auth / req.session, CSRF, rate limit e metadati di route.

28.4 Pipeline delle richieste

Ogni richiesta segue quest'ordine. Conoscerlo conta per le chiavi di auth, CSRF e validazione:

  1. Risolve il correlation ID: onora X-Correlation-ID in ingresso oppure ne genera uno; lo rimanda nella response
  2. Preflight CORS (OPTIONS) se CORS è abilitato, poi gli header CORS sulla richiesta reale
  3. Path statici di Swagger se abilitati
  4. Match della route; nessun match → envelope standard 404
  5. Parse del body per POST / PUT / PATCH
  6. CSRF (prima di qualsiasi middleware applicativo)
  7. Middleware globale (server.use)
  8. Middleware di route (@Use / @Middleware)
  9. Rate limit (dopo il middleware, così verifiedSub* vede req.auth)
  10. Schema @Validate
  11. Parameter binding e handler
  12. Serializzazione o commit della response

Gli handler interpretati girano su un interprete isolato per richiesta. In modalità interpret, assegnare req.tenant = "acme" nel middleware è visibile al middleware successivo e all'handler solo su quella richiesta.

28.5 Parameter binding

28.5.1 Path parameter

I placeholder nel pattern di route si legano per nome:

@GET("/api/users/{id}")
function getUserById(id) {
    var jsonStr = "{\"id\": \"" + id + "\", \"name\": \"Alice\"}";
    return parseJSON(jsonStr);
}

28.5.2 Query parameter

I nomi di parametro non corrispondenti si legano dalla query string:

@GET("/api/users")
function getUsers(limit, offset) {
    // 'limit' and 'offset' extracted from ?limit=10&offset=0
    var jsonStr = "{\"users\": [], \"limit\": " + limit + "}";
    return parseJSON(jsonStr);
}

28.5.3 Request body

Un parametro di nome body riceve il payload parsato. Content type:

  • application/json → oggetto / array (JSON non valido ricade sulla stringa grezza)
  • application/x-www-form-urlencoded → oggetto di campi stringa
  • qualsiasi altro → stringa grezza

RestServer non parsa multipart/form-data. Usa HttpServer per gli upload di file.

@POST("/api/users")
function createUser(body) {
    var name = body.name;
    var jsonStr = "{\"id\": 1, \"name\": \"" + name + "\"}";
    return parseJSON(jsonStr);
}

28.5.4 Nomi di parametro speciali

Questi nomi si legano sempre, sia in modalità name-based sia con i decoratori:

ParametroSi lega a
req / requestContesto della request
res / responseContesto della response
params / pathParamsOggetto dei path parameter
query / queryParamsOggetto dei query parameter
headersHeader della request
cookiesCookie della request
bodyBody parsato (modalità name-based)

28.5.5 Binding con decoratori

Rinomina opzionale. Se un qualsiasi parametro ha un decoratore, i parametri senza decoratore si legano a null (i nomi speciali sopra si legano comunque):

@PUT("/api/users/{id}/posts/{postId}")
function updatePost(@PathParam("id") userId, @PathParam("postId") postId, 
                    @QueryParam("limit") maxResults, @Body() updateData) {
    // userId = path param {id}
    // postId = path param {postId}
    // maxResults = query param ?limit=10
    // updateData = request body
}

In modalità transpile il compilatore registra le route con paramDecorators = null, quindi la rinomina @PathParam / @QueryParam / @Body funziona solo nell'interprete. Quando compili, preferisci far coincidere i nomi dei parametri con path/query/body.

28.6.2 req.auth

Preferisci req.auth.authenticateBearerJwt(secret) (API) o authenticateCookieJwt(cookieName, jwtSecret, cookieSecret?) (sessioni browser). Entrambi verificano il JWT, popolano claim/ruoli/permessi e lanciano un 401 standardizzato in caso di fallimento. Crea i token con createJwt (capitolo 13).

authenticateBearerJwt(secret)JWT Bearer in Authorization

function requireAuth(req, res, next) {
    req.auth.authenticateBearerJwt("my-jwt-secret");
    next();
}

@GET("/api/admin/stats")
function adminStats(req) {
    req.auth.requireRole("admin");
    return {
        "users": 2
    };
}

var server = new RestServer(8080);
server.use(requireAuth, {
    "except": ["/api/health", "/api/login"]
});
server.start();

Salta i path pubblici con use(middleware, { "except": [...] }). Sono supportati path esatti e prefissi con * finale. Gli alias di ingress X-Malda-Auth-Verified / X-Malda-Auth-Sub (e i legacy X-Auth-* / X-Verified-Sub) possono pre-marcare un subject; il middleware applicativo dovrebbe comunque chiamare authenticate* così ruoli e claim sono presenti.

28.7 Gestione della response

28.7.1 Forme di return

  • Oggetto / array semplice → JSON 200
  • Stringa semplice → text/plain 200
  • { "status": 201, "data": ... } → status HTTP da status; quel campo viene rimosso dal body JSON
  • Oggetto di errore standard {status, error, message} (vedi 28.11) → quello status, body invariato
  • res.status(...).json(...) (o altri helper di send) → già committed; il valore di return viene ignorato
@POST("/api/users")
function createUser(body) {
    var jsonStr = "{\"status\": 201, \"data\": {\"id\": 1, \"name\": \"" + body.name + "\"}}";
    return parseJSON(jsonStr);  // Returns 201 Created
}
@GET("/api/users/{id}")
function getUser(req, res) {
    var id = req.params.id;
    return res.status(200).json(parseJSON("{\"id\": \"" + id + "\"}"));
}

28.7.2 API helper di response

MembroNote
status(code)Imposta lo status; concatenabile
json / text / html / redirect / send / sendBase64 / fragmentInviano e chiudono subito
header(name, value), setContentType(type)Header prima del send
cookie(name, value, options?), clearCookie(name, options?)Default: HttpOnly=true, Secure=true, SameSite=Lax, Path=/. Opzioni: domain, maxAge, sameSite, httpOnly, secure, path
flush()Invia ciò che è già committed (anche solo status)
statusCode, contentType / type, headers, bodySnapshot in lettura
committed / sent / isCommitted, flushed / isFlushedStato di invio

res.send(value) codifica il body come stringa UTF-8. Usa res.sendBase64(b64) per payload binari (PDF, DOCX e simili): decodifica la stringa base64 e scrive quei byte. Base64 non valido genera un errore.

Dopo un helper di send, l'handler può continuare (lavoro in background). Header e cookie impostati dopo il send lanciano response already sent. res.fragment(targetId, html) è la forma early-send di componentFragment(targetId, html): stessi header X-Malda-Fragment, ma il client riceve il fragment prima che l'handler ritorni.

28.8 Middleware

Usa server.use(...) per il middleware globale. Il contratto è (req, res, next). Chiama next() per continuare; ometterlo interrompe la catena. @Use("name") a livello di route gira dopo il middleware globale e prima della validazione + handler. Le app transpile dovrebbero passare il nome della funzione come stringa: server.use("requireAuth").

function logRequest(req, res, next) {
    print(req.method + " " + req.path);
    next();
}

var server = new RestServer(8080);
server.use(logRequest);
server.start();

28.9 CSRF, rate limiting e proxy fidato

var server = new RestServer(8080);
server.enableCsrf("my-csrf-secret");                 // cookie: csrf_token, header: X-CSRF-Token
server.setRateLimit(120, 60, "verifiedSubOrIp");     // after auth middleware; prefer subject when verified
server.setRateLimitHeaders(true, true);              // add X-RateLimit-* + Retry-After headers
server.configureTrustedProxy(true, "X-Forwarded-For", 0); // trust first forwarded hop
server.use(requireAuth, { "except": ["/api/health", "/metrics"] });
server.start();

Il CSRF gira prima del middleware. I metodi sicuri (GET/HEAD/OPTIONS) emettono o aggiornano il cookie CSRF quando manca o non è valido. I metodi che cambiano stato (POST/PUT/PATCH/DELETE) richiedono cookie + token di richiesta corrispondenti da X-CSRF-Token, body.csrfToken o body._csrf. Abbinalo a generateCsrfToken / csrfField del capitolo 13 per i client browser.

Il rate limiting gira dopo il middleware globale e di route. Le strategie verifiedSub* usano come chiave il subject impostato da authenticateBearerJwt / authenticateCookieJwt; altrimenti ricadono su IP/token. user usa l'header X-User-Id. Gli header del proxy sono ignorati finché non abiliti configureTrustedProxy(...).

I fallimenti di CSRF, auth e rate-limit usano l'envelope di errore standard e includono il correlation ID.

28.10 Validazione

@Validate(...) controlla path, query e body prima dell'handler. Le richieste non valide restituiscono HTTP 400 con details a livello di campo e non eseguono la logica dell'handler. I valori di schema possono essere una stringa JSON o un oggetto. Le regole sono una DSL a pipe (int|required|min=1) oppure un oggetto {type, required, min, max, minLength, maxLength, pattern}.

@GET("/search/{id}")
@Validate("{\"path\":{\"id\":\"int|required|min=1\"},\"query\":{\"q\":\"string|required|minLength=2\"}}")
function search(id, q) {
    return parseJSON("{\"ok\": true}");
}

Per controlli che dipendono da dati già caricati, chiama req.requireValid(schema) o req.validate(schema) dentro l'handler. Gli item di details della validazione sono {location, field, message}. Quando Swagger è abilitato, i metadati di @Validate si riflettono negli schema OpenAPI di parameter e request-body.

28.11 Gestione degli errori

I fallimenti del framework (404, CSRF, auth, rate limit, @Validate / req.requireValid, errori non gestiti dell'handler) usano un unico contratto JSON:

{
  "status": 401,
  "error": "InvalidToken",
  "message": "Invalid token signature.",
  "correlationId": "...",
  "details": [ ... ] // optional, present for validation errors
}
  • Header di response: X-Correlation-ID (onora un valore in ingresso)
  • Campo del payload: correlationId
  • details di validazione: array di {location, field, message}
  • Imposta MALDA_WEB_DEBUG_ERRORS=1 (o true) per aggiungere un oggetto diagnostics sui 500

Una route mancante è {"status": 404, "error": "NotFound", ...}. Un throw non gestito di un oggetto semplice non è uno status HTTP personalizzato: diventa 500 InternalServerError. Per inviare un errore client strutturato, restituisci l'envelope standard oppure usa res.status(code).json(...):

@GET("/api/users/{id}")
function getUserById(id, res) {
    if (!userExists(id)) {
        return {
            "status": 404,
            "error": "NotFound",
            "message": "User not found"
        };
    }
    return res.json({
        "id": id
    });
}

req.auth.requireRole, requirePermission, requireVerified e req.requireValid lanciano già quell'envelope.

28.12 CORS e Swagger/OpenAPI

var server = new RestServer(8080);
server.enableCORS(true);
server.setCORSOrigin("*");
server.setCORSMethods(["GET", "POST", "OPTIONS"]);
server.setCORSHeaders(["Content-Type", "Authorization"]);
server.enableSwagger(true);
server.start();

// OpenAPI JSON: /swagger.json, /openapi.json, /swagger/openapi.json

Con Swagger abilitato, GET su quei tre path (stesso documento). I vincoli di validazione di @Validate compaiono negli schema generati.

28.13 Mount su HttpServer

Per un unico listener che serve prima le route API e poi pagine/componenti/file statici, costruisci un RestServer deferred e fanne il mount. Non dare all'API una porta propria e non chiamare start() come listener standalone prima del mount.

var api = new RestServer();
var web = new HttpServer(8080);

function requireAuth(req, res, next) {
    req.auth.authenticateBearerJwt(jwtSecret);
    next();
}

@GET("/api/health")
function health() {
    return {
        "status": "ok"
    };
}

web.mount(api);
web.enableSession(sessionSecret);
api.enableCsrf(csrfSecret);
api.setRateLimit(200, 60, "verifiedSubOrIp");
api.use(requireAuth, {
    "except": ["/api/health"]
});
web.start();
  • Configura CSRF, rate limit e middleware API sull'istanza RestServer
  • I cookie di sessione stanno spesso su HttpServer (pagine + API condividono il listener)
  • Un api.start() montato non fa bind di una porta; marca solo l'API come in esecuzione con l'host
  • Un RestServer che ha già un proprio listener non può essere montato
  • Starter canonico: malda new fullstack → Templates/fullstack/backend/app.malda

28.14 Interpret vs transpile

  • Il binding per nome, @RouteGroup / @Version / @Use / @Validate e req/res funzionano in entrambe le modalità
  • La rinomina @PathParam / @QueryParam / @Body è solo interpret (vedi 28.5.5)
  • In transpile, @GET e @POST vengono registrati anche su HttpServer. Un processo compilato che costruisce entrambi i server può vedere le stesse route GET/POST su ciascuno
  • In transpile passa il middleware a use come stringa nome-funzione: server.use("requireAuth", { "except": ["/api/health"] })
  • @Use a livello di route prende sempre una stringa nome di funzione
