33. Property testing

MALDA supporta dichiarazioni property a livello di linguaggio per il testing generativo deterministico, basato su seed, tramite malda test.

33.1 Dichiarare ed eseguire le property

property intIdentity(x) {
    return (x + 0) == x;
}

Esegui le property con metadati di replay deterministici:

malda test --iterations 100 --seed 1337

33.2 Fallimento → controesempio ridotto (shrunk) → artefatto di regressione

Usa seed deterministici per fallimenti riproducibili, poi abilita in opt-in la generazione degli artefatti per catturare il controesempio canonico (shrunk) come file di regressione autonomo.

# Run property tests with deterministic replay metadata
malda test ./tests --iterations 100 --seed 1337

# Generate regression artifacts for failing properties
malda test ./tests --iterations 100 --seed 1337 --write-regression

# Optional custom output directory
malda test ./tests --write-regression --regression-dir ./artifacts/regressions

# Emit CI JSON consumed by IDE/Desktop "Create Regression" action
malda test ./tests --format ci --iterations 100 --seed 1337

La posizione di default degli artefatti è tests/regressions. I file generati sono artefatti di riproduzione deterministici .spec.malda e MALDA stampa ogni path con Generated regression: ....

L'azione IDE/Desktop Create Regression tratta i suggerimenti CI come non attendibili: i path raccomandati vengono sanitizzati e limitati al workspace attivo prima di scrivere i file.

Il JSON CI include campi di metadati delle property per le integrazioni di tooling, tra cui shrunkCounterexample, canGenerateRegression e recommendedRegressionPath.

33.3 Eseguire una property dentro uno script

Puoi eseguire una property dichiarata direttamente dentro uno script MALDA usando runProperty(name, iterations?, seed?).

property stableIdentity(x) {
    return (x + 0) == x;
}

var result = runProperty("stableIdentity", 40, 1337);
print("Passed: " + string(result.passed));

runProperty(...) restituisce un oggetto con questi campi:

  • propertyName, passed, iterations, seed
  • failedTrial, error, counterexample, shrunkCounterexample

33.4 Modello di capability

Le property possono dichiarare requisiti di capability e target di backend espliciti usando i decoratori:

@requires("core", "actors")
@targets("interpreter", "csharp", "js")
property actorSafetyInvariant(x) {
    return x == x;
}
  • @requires(...): dichiara i tag di capability richiesti dalla property.
  • @targets(...): dichiara le modalità di backend in cui la property è attesa.

I tag di modulo di capability supportati per @requires(...) sono:

  • Interprete: core, file-io, actors, workflows, dotnet-interop, host-interop
  • CSharp: core, file-io, actors, workflows, dotnet-interop, host-interop
  • JS: core, web-dom, game-canvas

Se una property richiede una capability non supportata da un backend, quel backend viene riportato come non applicabile (non come fallimento).

La matrice di capability è la fonte di verità per l'idoneità dei backend tra interpreter, csharp e js.

33.5 Limitazioni JavaScript e semantica di skip

La parità del backend JavaScript è condizionata dalle capability. Se una property richiede capability JS non supportate, MALDA riporta la modalità JS come non applicabile con un motivo. Questo non conta come fallimento di parità per i backend supportati.

Per le property idonee a JS in cui un harness JS delle property non è ancora abilitato, MALDA riporta JS come skipped con un motivo esplicito in stile TODO, invece di far fallire la parità.
