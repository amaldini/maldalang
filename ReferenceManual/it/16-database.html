16. Supporto database

MALDA distribuisce tre client con la stessa API: SqliteClient, SqlServerClient e PostgresClient. Parti da SQLite: è un file su disco (o un database in memoria), senza server. Connessione, SQL parametrizzato, query builder, insert e transazioni sono identici sugli altri due; cambiano solo connection string e sintassi dei placeholder.

I client funzionano con l'interprete e il transpile C#. Non sono disponibili sul backend JavaScript — tieni il SQL sul server e chiamalo via HTTP dal codice nel browser. Vedi 2. Strumenti e toolchain (modi di runtime) e la matrice delle capacità dei backend.

Questo capitolo è l'API dei client SQL. Lo storage dei workflow durevoli è un file SQLite separato sotto .malda/ — vedi 22. Workflow durevoli. La similarity search è 15. VectorDB, non questi client.

16.1 SQLite da zero

Connetti, crea una tabella, inserisci, interroghi, disconnetti. I parametri usano @name (non concatenare mai input utente nel SQL). Data Source=:memory:; è un database in memoria che scompare alla disconnessione — usalo nei test e negli snippet così non resta nulla su disco.

var db = new SqliteClient();
db.connect("Data Source=:memory:;");
print(db.isConnected);

db.execute("CREATE TABLE users (id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT, age INTEGER)");
db.insert("users", {name: "Alice", age: 30});

var one = db.queryOne("SELECT name, age FROM users WHERE name = @name", {name: "Alice"});
print(one.name);
print(one.age);

var allRows = db.query("SELECT name FROM users");
print(allRows.length);

db.disconnect();
print(db.isConnected);

Costruttore: new SqliteClient() oppure new SqliteClient(connectionString). Passare la stringa al costruttore non apre la connessione — devi comunque chiamare connect(connectionString). I database su file usano Data Source=path/to/db.sqlite; (i path relativi si risolvono dalla working directory del processo).

Stesso file nel catalogo: Examples/Databases/sqlite_basic.malda (stampa l'API senza connettersi). Uno starter reale su file è malda new webapi --local-first / malda new fullstack --local-first.

16.2 API condivisa dei client

Tutte e tre le classi espongono gli stessi metodi. Chiama connect prima di qualsiasi altra cosa; il SQL prima del connect lancia Not connected to database. Call connect() first.

MembroRestituisceNote
connect(connectionString)—Apre (o riapre) la connessione
disconnect()—Chiude la connessione; fa rollback di una transazione aperta
isConnectedboolProperty, non un metodo
query(sql, params?)array di oggetti rigaZero righe → []
queryOne(sql, params?)una riga o nullSolo la prima riga che corrisponde
execute(sql, params?)int (righe interessate)DDL, INSERT/UPDATE/DELETE, PRAGMA
select(...columns)il client (catena)Avvia il query builder; vedi 16.3
insert(table, values)int (righe interessate)values è un oggetto non vuoto
beginTransaction() / commit() / rollback()—Vedi 16.4

I risultati delle query sono array di oggetti le cui property sono i nomi delle colonne restituiti dal driver (alias compresi). Il NULL SQL diventa null MALDA. Interi e float restano numerici; i valori SQLite DATETIME tornano come stringhe yyyy-MM-dd HH:mm:ss.

var users = db.query("SELECT name, email FROM users WHERE age > @age", {age: 25});
print(users[0].name + " - " + users[0].email);

var missing = db.queryOne("SELECT name FROM users WHERE id = @id", {id: -1});
print(missing == null);

Gli oggetti parametro accettano chiavi con o senza @: {age: 25} e {"@age": 25} legano entrambi @age su SQLite e SQL Server. PostgreSQL usa $1, $2, … — vedi 16.5. Non esiste una property lastInsertId sul client; insert / execute restituiscono il conteggio delle righe interessate. Leggi la nuova chiave con SQL (16.6).

16.3 Query builder

Il builder è un piccolo helper sullo stesso client, non un dialetto SQL separato. Copre SELECT più INSERT / UPDATE / DELETE con valori parametrizzati. Non ci sono orderBy, limit, join né OR — per quelli usa SQL grezzo.

16.3.1 Select

select(...columns).from(table).where(...).query() esegue il SELECT costruito. query() senza argomenti chiude il builder; query(sql, params?) resta SQL grezzo. where(column, value) significa =; where(column, operator, value) passa l'operatore così com'è (>, <, !=, LIKE, …). Le chiamate where successive si combinano con AND.

var db = new SqliteClient();
db.connect("Data Source=:memory:;");
db.execute("CREATE TABLE users (id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT, email TEXT, age INTEGER)");
db.insert("users", {name: "Jane", email: "jane@example.com", age: 30});
db.insert("users", {name: "Bob", email: "bob@example.com", age: 20});

var adults = db.select("name", "email")
            .from("users")
            .where("age", ">", 25)
            .query();
print(adults.length);
print(adults[0].name);
db.disconnect();

Ogni colonna in where dovrebbe essere unica: i nomi dei parametri derivano dalla colonna, quindi due condizioni sulla stessa colonna si sovrascrivono. Il builder concatena nomi di tabella e colonna nel SQL; solo i valori sono parametrizzati. Non mettere input utente in quei nomi.

16.3.2 Insert, update, delete

insert(table, values) è una chiamata unica — non usa un where precedente.

update(table, values) e delete(table) richiedono prima una catena select / from / where che abbia popolato il builder. Chiama where prima, poi update o delete. Concatenare .update(...) dopo .where(...) è la stessa cosa, perché quei metodi restituiscono il client. Chiamare update / delete senza un where lancia un errore. Non esiste la forma «update e poi where».

var db = new SqliteClient();
db.connect("Data Source=:memory:;");
db.execute("CREATE TABLE users (id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT, age INTEGER)");
db.insert("users", {name: "Jane", age: 30});
db.insert("users", {name: "Bob", age: 20});

db.select("name").from("users").where("name", "Bob").update("users", {age: 21});
var bob = db.queryOne("SELECT age FROM users WHERE name = @name", {name: "Bob"});
print(bob.age);

db.select("name").from("users").where("name", "Bob").delete("users");
print(db.query("SELECT name FROM users").length);
db.disconnect();

16.4 Transazioni

Una transazione alla volta per client. Un secondo beginTransaction() lancia Transaction already in progress. commit() / rollback() senza una transazione aperta lanciano No transaction in progress. disconnect() fa rollback se una transazione è ancora aperta.

var db = new SqliteClient();
db.connect("Data Source=:memory:;");
db.execute("CREATE TABLE t (name TEXT)");

db.beginTransaction();
db.execute("INSERT INTO t (name) VALUES (@name)", {name: "Temp"});
db.rollback();
print(db.query("SELECT name FROM t").length);

db.beginTransaction();
try {
    db.execute("INSERT INTO t (name) VALUES (@name)", {name: "Keep"});
    db.commit();
} catch (e) {
    db.rollback();
}
print(db.query("SELECT name FROM t").length);
db.disconnect();

16.5 SQL Server e PostgreSQL

Stessi metodi, connection string e placeholder diversi. Il query builder numera da solo i parametri PostgreSQL, quindi select / from / where / insert hanno lo stesso aspetto di SQLite; solo il SQL grezzo usa $1.

SQLite / SQL ServerPostgreSQL
ClasseSqliteClient / SqlServerClientPostgresClient
Connection stringSQLite: Data Source=app.db; oppure Data Source=:memory:;
SQL Server: Server=localhost;Database=mydb;User Id=user;Password=pass;
Auth Windows: Server=localhost;Database=mydb;Integrated Security=true;		Host=localhost;Database=mydb;Username=user;Password=pass;
Con porta: aggiungi Port=5432;
Placeholder nel SQL grezzo@age con {age: 25}$1 con {$1: 25}
 
var sql = new SqlServerClient();
sql.connect("Server=localhost;Database=mydb;User Id=user;Password=pass;");
var rows = sql.query("SELECT * FROM users WHERE age > @age", {age: 25});
sql.disconnect();

var pg = new PostgresClient();
pg.connect("Host=localhost;Database=mydb;Username=user;Password=pass;");
var rows2 = pg.query("SELECT * FROM users WHERE age > $1", {$1: 25});
pg.disconnect();

Campioni del catalogo (stampano l'API, non si connettono): Examples/Databases/sql_server_basic.malda, Examples/Databases/postgres_basic.malda.

16.6 Id delle righe inserite e colonne JSON

Dopo un insert, chiedi al database la nuova chiave. SQLite:

var db = new SqliteClient();
db.connect("Data Source=:memory:;");
db.execute("CREATE TABLE t (id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT)");
db.execute("INSERT INTO t (name) VALUES (@name)", {name: "A"});
var row = db.queryOne("SELECT last_insert_rowid() AS id");
print(row.id);
db.disconnect();

SQL Server usa in genere SELECT SCOPE_IDENTITY() AS id nella stessa sessione (dentro una transazione se ci sono altri writer). PostgreSQL può fare INSERT … RETURNING id e queryOne su quell'istruzione. Nessuno di questi è un campo del risultato MALDA di insert.

Il JSON in una colonna TEXT è una stringa ordinaria: scrivi con toJSON, leggi con parseJSON. Gli alias nella lista SELECT diventano i nomi delle property MALDA.

var db = new SqliteClient();
db.connect("Data Source=:memory:;");
db.execute("CREATE TABLE settings (key TEXT PRIMARY KEY, value_json TEXT NOT NULL)");
var payload = toJSON({title: "ACME", ok: true});
db.execute("INSERT INTO settings (key, value_json) VALUES (@key, @value)", {key: "brand", value: payload});
var row = db.queryOne("SELECT value_json AS valueJson FROM settings WHERE key = @key", {key: "brand"});
var parsed = parseJSON(row.valueJson);
print(parsed.title);
print(parsed.ok);
db.disconnect();

I pragma SQLite passano da execute come qualsiasi altro SQL. Gli scaffold local-first attivano WAL e foreign key:

db.execute("PRAGMA journal_mode = WAL");
db.execute("PRAGMA foreign_keys = ON");

16.7 Runtime, errori e backend

  • Un SQL fallito è un errore di runtime il cui messaggio inizia con SQL query error: oppure SQL execute error: più il testo del driver.
  • Richiama connect chiude la connessione precedente e apre la nuova stringa.
  • Il transpile JavaScript non emette questi client. La UI nel browser deve chiamare un backend MALDA REST o @PAGE che possiede il database — vedi 26. Backend UI JavaScript nel browser e 27. Server REST API.
  • I workflow, la coda dei job e GraphMemory persistono su file propri; non puntare SqliteClient a .malda/workflows.db a meno che tu non lo stia ispezionando come DBA.

16.8 Sicurezza

Tutti e tre i client inviano i valori come parametri. Passa sempre un oggetto invece di concatenare stringhe nel SQL.

Importante: Non concatenare mai input utente direttamente nelle query SQL. Usa sempre query parametrizzate per prevenire attacchi di SQL injection. Il query builder parametrizza solo i valori — nomi di tabella, nomi di colonna e operatori sono copiati nell'istruzione così come scritti.

16.9 malda db (scaffold local-first)

malda db è una CLI per progetti SQLite local-first generati dallo scaffold (malda new webapi --local-first oppure malda new fullstack --local-first). Non è uno strumento di migration generico per programmi SqliteClient arbitrari. Di default legge config/data.example.json per databaseFile e migrationModule.

malda db status
malda db migrate
malda db seed
malda db rollback
malda db --help
  • status — ispeziona il file SQLite e il registro delle migration senza scrivere (id applicato più recente, supporto seed/rollback, drift sorgente-vs-database). --format json / --json per le macchine.
  • migrate — applica le voci in sospeso da localMigrationRegistry tramite initLocalDataPlatform() / runLocalMigration<ID>().
  • seed — migra, poi inserisce righe starter idempotenti da seedLocalDataPlatform().
  • rollback — revert solo dell'ultima voce del registro applicata che esiste ancora nel sorgente, tramite openLocalDataPlatform() e rollbackLocalMigration<ID>().

Flag opzionali: --project / -p (root del progetto), --module / -m (path del .malda di migration), --database / -d (file SQLite). Preferisci cambiamenti di schema additivi e idempotenti con gli helper generati (ensureColumn, ensureIndex, ensureLifecycleColumns) invece di SQL di avvio ad hoc. Seed e rollback seguono quelle convenzioni dello scaffold; non scoprono layout arbitrari.
