23. Esecuzioni agentiche

I capitoli 10 e 18 insegnano a chiamare un modello e a orchestrare agenti. Questo capitolo è lo strato delle cinture di sicurezza: come testare, registrare, limitare nel tempo, ricordare, restringere e diagnosticare quelle esecuzioni così restano economiche, ripetibili e abbastanza sicure per il lavoro quotidiano e per la CI.

Una funzione ordinaria è deterministica: stesso input, stesso output. Un prompt no. Il modello può cambiare le parole, spendere token, chiamare tool, bloccarsi o inventare un path. Serve quindi un macchinario extra che la programmazione ordinaria non usava — non perché MALDA sia più difficile, ma perché l'ospite (il modello) è imprevedibile.

Interprete e transpile C# coincidono sugli esempi offline di questo capitolo. JavaScript è solo host (n/a).

Cosa ti serve già

Leggi questo capitolo dopo aver scritto un prompt con uno schema e aver chiamato evalPrompt (senza API key). Non ti serve un modello live per imparare suite, journal, context, policy, AgentError, stream o grounded.wrap. Le chiamate live compaiono solo quando registri una cassetta o fai await di un prompt.

23.1 Suite di eval

Una suite è un gruppo nominato di case di eval — pensali come unit test per i prompt. Ogni case passa una fixture (JSON finto del modello) nello stesso percorso extract / validate che userebbe await, poi fa expect di un booleano. Niente API key, niente rete, niente testo a sorpresa.

Per questo malda run / l'interpretazione ordinaria salta le suite (come property): non fanno parte dell'output del programma. Si eseguono con malda eval. Non è malda test, che scopre le dichiarazioni property e i file *.test.malda — vedi 35. Property testing.

23.1.1 La suite più piccola

Tre pezzi lavorano insieme:

  1. Uno schema nomina la forma che vuoi indietro (name: string).
  2. Un prompt con -> Card è solo un template finché non fai await. Qui non facciamo mai await.
  3. evalPrompt(instance, fixture) finge che il modello abbia restituito fixture e percorre lo stesso coerce di await.

Lookahead dopo case: case "title" { è un case di suite; case Pattern: è un braccio di match. Il titolo tra virgolette è il nome che vedrai nel report di eval.

schema Card {
    name: string;
}

prompt extract(raw) -> Card {
    user: raw;
}

suite "extract" {
    case "offline shape" {
        var checked = evalPrompt(extract("x"), dict { "name": "Ada" });
        expect(checked.ok);
    }
}

print("ok");

Passo passo: extract("x") costruisce un PromptInstance (ancora nessun modello). Il dict { "name": "Ada" } è il completamento finto. evalPrompt controlla quel dict contro Card e torna { ok, data } oppure { ok: false, error }. expect(checked.ok) lancia come assert se la condizione è falsa, e quel sample fallisce. Il print("ok") dopo la suite gira comunque con malda run perché la suite stessa viene saltata.

validate è il cugino più quieto: torna { ok, error } e non lancia sul mismatch. Usa expect dentro i case (fallire il sample). Usa validate nel codice ordinario quando vuoi fare branch.

expect(1 + 1 == 2);
print("ok");

23.1.2 Come eseguirla

malda eval Examples/Prompts/eval_suite_offline.malda
malda eval path.malda --baseline .malda/evals.json
malda eval path.malda --baseline .malda/evals.json --update-baseline
  • Prima riga: esegue ogni suite del file. Exit non-zero se un case fallisce.
  • --baseline: confronta i pass rate di questa run con un JSON salvato. Un case il cui pass rate cala fa fallire il processo (hai peggiorato il prompt).
  • --update-baseline: scrive i rate attuali in quel file dopo una run di cui ti fidi. Fallo di proposito, non per nascondere una regressione.

23.1.3 Decorator opzionali sui case

Stanno su un case (o sulla suite) quando più avanti passi dalle fixture ai sample live:

  • @samples(N) — sotto MALDA_REPLAY, replay di N varianti registrate; senza replay, N sample live. N <= 1 gira una volta.
  • @threshold(0.9) — exit non-zero quando il pass rate del case è sotto la soglia (qui 90%). Utile quando un modello live può fallire un sample raro.
  • @judge(prompt gradeHelpfulness) — dopo un body che passa, valuta l'espressione judge (un prompt viene chiamato con il titolo del case). Un oggetto risultato con ok: false fallisce il sample. Il judge è un secondo prompt che valuta il primo.

Stesso file: Examples/Prompts/eval_suite_offline.malda. Snippet per agenti: docs/llm/few-shot/43_eval_suite.malda.

Errori comuni. Lanciare il file con un malda semplice e concludere “la suite è rotta” — è stata saltata. Usare malda test (property test) al posto di malda eval. Chiamare await extract(...) dentro un case quando volevi evalPrompt (serve un modello o una cassetta). Trattare validate come asserzione di test — non fallisce il case finché non fai expect(r.ok).

23.2 Cassette

Una cassetta è un nastro del traffico LLM: ogni Chat (HTTP, GGUF, client bridge) si può registrare in un file JSONL e riascoltare dopo. Pensa a un VCR. Registra una volta mentre hai una key e la rete; riascolta per sempre in aula e in CI senza spendere token e senza dipendere dall'umore del vendor.

I segreti (Authorization, API key, stringhe evidentemente secret-shaped) vengono redatti in registrazione, così il file è più sicuro da committare di un log grezzo. Come registrare: tests/cassettes/README.md.

23.2.1 Registra, poi riascolta

MALDA_RECORD=tests/cassettes/name.jsonl   malda Examples/path.malda
MALDA_REPLAY=tests/cassettes/name.jsonl   malda Examples/path.malda
MALDA_REPLAY_STRICT=1                    malda Examples/path.malda
  1. MALDA_RECORD — esegui il programma sul serio. Ogni Chat viene appeso al file JSONL.
  2. MALDA_REPLAY — la run successiva cerca ogni Chat in quel file e restituisce la risposta salvata.
  3. MALDA_REPLAY_STRICT=1 — un miss di lookup è un errore duro. Senza, un miss scrive cassette_miss nel journal e l'host chiama il modello live. Questo è il footgun: una CI che “riascolta” può comunque spendere soldi.

23.2.2 Cosa rende due chiamate “la stessa”

La chiave della cassetta è hash del prompt + args canonici + model + mode (A/B/C) + hash dello schema. Cambi il testo del prompt, gli argomenti, il nome del modello, il mode dei tool o lo schema, e ottieni una chiave nuova — un miss di replay. È voluto: non devi riusare in silenzio una risposta registrata per un'altra domanda.

Regola CI. Imposta sempre MALDA_REPLAY_STRICT=1 accanto a MALDA_REPLAY nelle pipeline. Un miss deve far fallire il job, non telefonare al vendor.

Examples/Agents/agent_governance_golden.malda è una coppia interpret/transpile offline (niente cassetta). Examples/RalphWiggum/RalphWiggum.malda resta n/a (too-large).

23.3 Journal di run

Il journal di run è un scatola nera in-process. Una lista raccoglie eventi prompt, tool, cap, hop e step di workflow per il processo corrente. Dopo una run puoi chiedere “cosa è successo?” senza raschiare stdout.

SQLite dei workflow resta lo store di durabilità per le istanze longeve (vedi 22). Gli step riusciti vengono anche specchiati qui così trace.journal() e gli eventi di workflow condividono un substrato. Il journal non è una cassetta: non riascolta le risposte del modello; ricorda solo che una chiamata è avvenuta.

23.3.1 Leggilo dopo un prompt offline

schema Card {
    name: string;
}

prompt extract(raw) -> Card {
    user: raw;
}

var checked = evalPrompt(extract("Ada"), dict { "name": "Ada" });
var events = trace.journal();
print(events.length > 0);

evalPrompt basta per far atterrare un evento di journal — non serve un Chat live. Ogni evento è un oggetto con ts, span, kind (prompt / tool / cap / hop / step), name, opzionali promptHash / model / tokens / cost / ms / repairs / error, e ok.

  • trace.span("name", fn) — annida gli eventi sotto quel nome di span (una regione etichettata, come una cartella nel log).
  • trace.lastUsage() — ultimo oggetto token/cost/ms registrato, oppure null se non è ancora stato fatturato nulla.
  • .usage su un risultato di prompt è metadata. Una chiave propria nominata usage (campo di schema) vince — se lo schema ha un campo usage, quel campo è il valore, non i metadata di billing.

Export: MALDA_TRACE=jsonl|otlp più MALDA_TRACE_FILE opzionale. Non è il CLI malda trace esistente, che continua a leggere i file di sessione .malda-trace.jsonl. Stesso file: Examples/Prompts/run_journal_offline.malda.

Tre “trace” diversi. trace.journal() è questa lista in-process. MALDA_TRACE esporta quella lista. malda trace è un CLI più vecchio che legge file di sessione. Parti da trace.journal() nel programma; aggiungi la env var quando vuoi gli stessi eventi su disco.

23.4 Scope within

Lo statement within (30s) { … } è un timer da cucina a orologio da parete. Quando suona, il runtime scrive un timeout nel journal e lancia Timeout: exceeded within (…ms). La cancellazione entra in Chat LLM e nel consume dei cap, così una chiamata al modello bloccata o un tool lento non restano in esecuzione per sempre nel processo.

Le unità sono un numero più ms, s o m (convertite in millisecondi). Un nudo within (30) è un errore di parse — scrivi 30s o 30000ms. L'opzionale budget(tokens: N, tools: N, cost: N?) spinge un budget di risorse nidificato come @budget.

23.4.1 Statement vs decoratore

FormaDoveArgomento
within (30s) { … }Uno statement intorno a un blocco qualsiasiNumero + ms / s / m
@within(5000)Decoratore su una funzione o su thinkSolo millisecondi, senza suffisso di unità

Il decoratore @within(ms) resta la deadline per funzione / per think. Non è uno statement e prende solo millisecondi. Vedi 10. Prompt e 9.7 Decoratori.

within (10ms) {
    sleep(50);
}

print("should-not-print");

Questo blocco deve fallire. Alla scadenza il runtime scrive un timeout e lancia; il print non viene mai raggiunto. Stesso file: Examples/Prompts/within_sleep.malda (interprete e C# falliscono entrambi — una coppia sull'identità dell'errore, non su stdout).

23.4.2 Race fra più rami

Quando avvii più pezzi di lavoro temporizzati, questi builtin scelgono un vincitore:

  • race(tasks…) — primo ramo completato, anche se quel ramo è un timeout.
  • firstOk(tasks…) — primo ramo che non è una variante Timeout (salta quelli che hanno finito il tempo).
  • all(tasks…) aspetta ogni ramo. Un ramo fallito diventa uno slot AgentError Upstream; la chiamata non rilancia il primo errore. Ispezioni gli slot tu.
  • cancelWorkflow(id) mette un'istanza di workflow durevole in cancelled; il body interroga quello status fra gli statement. È un controllo di workflow, non un timer within — vedi 22.4.
Errori comuni. Scrivere @within(30s) (il decoratore non prende un'unità). Scrivere within (30) { } (servono ms/s/m). Aspettarsi che sleep dentro within torni normalmente — lancia. Trattare race come “primo successo”; quello è firstOk.

23.5 context dichiarato

Una chat è una lista di turni che cresce. I modelli hanno un limite di token; se tieni ogni messaggio per sempre, le chiamate successive diventano più lente, costano di più e alla fine falliscono. Una dichiarazione context Name { … } è un mini-DSL in stile schema per le regole di casa del taccuino: quanti turni tenere, cosa non droppare mai, e come restringere il resto.

new Name() costruisce un oggetto journaled con .add e .turns. Decidi ancora tu quando mandare quei turni a un prompt; l'oggetto context li memorizza e li taglia soltanto.

context Session {
    budget: 800 tokens;
    pin: systemFacts;
    retain: last 2;
    evict: oldest;
}

var s = new Session();
s.add("user", "hi");
s.add("user", "there");
print(s.turns.length >= 1);

s.add("user", "hi") appende un turno { role, content }. L'argomento singolo s.add("hi") è lo stesso del role user. Dopo ogni add, se la lista è più lunga della finestra retain (più gli slot pinned), il runtime scrive un evento context.compact e fa evict.

CampoSignificato
budget: N tokensMemorizzato sull'istanza (pin informativo). Da solo non abortisce un Chat.
pin: name, …Slot riservati che restano (fatti di sistema, le istruzioni originali).
retain: last NQuanti turni recenti tenere oltre a quelli pinned.
evict: oldest | lowestScore | noneCosa droppare quando la finestra trabocca. none continua a crescere.
compact: prompt summarizePrompt nominato opzionale. La compaction è una chiamata al modello registrata (chiave da cassetta), poi evict. Offline / nessun client: droppa solo i più vecchi.

WF1006: compaction / mutazione del context dentro il body di un workflow deve stare in uno step. Altrimenti il replay aggiungerebbe lo stesso turno due volte. I callee importati o sconosciuti restano Info, come WF1005. Vedi 22. Workflow durevoli.

Non è il this / context di JavaScript, e non è una variabile MALDA nominata context. var context = 1; resta una variabile normale. Solo la forma di dichiarazione context Name { … } crea questo oggetto.

23.6 policy al confine del programma

Il capitolo 12.6 dà a un tool una chiave (un capability token) così non può inventare un path. Una policy { … } a livello di file è la regola del palazzo sopra: anche se un token è stato mintato, il consume può comunque essere rifiutato. La violazione scrive un evento cap e lancia ToolDenied: ….

La policy è enforced sul consume dei cap indipendentemente da quali tool l'host ha registrato. È l'ultimo cancello prima che filesystem, rete, shell o MCP succedano davvero.

policy {
    fs:    readOnly under "./work";
    net:   allow "api.example.com", "*.internal";
    shell: deny;
    mcp:   allow "local";
}

Una policy che deny solo la shell basta per vedere la dichiarazione parsare e girare:

policy {
    shell: deny;
}

print("ok");

23.6.1 I quattro verbi

VerboSignificato
denyRifiuta sempre quel dominio (fs / net / shell / mcp).
allowPermette, opzionalmente solo i pattern di path o host elencati.
readOnlyCome allow, ma le write sono rifiutate. under "./work" limita l'albero.
approveRichiede MALDA_POLICY_APPROVE=1 (o true) oppure un ApprovalCallback dell'host. Non c'è ancora un prompt interattivo in stile workflow. Senza quelli, approve deny.

23.6.2 Policy vs @effects vs token

Tre strati che è facile comprimere in una sola parola “capability”:

StratoQuando giraA quale domanda risponde
@effects("pure") / "io" / "cap"Prima che il programma giri (check statico)Questa funzione può menzionare nomi I/O?
Capability token (cap.fileRead)Quando minti / consumiQuale unico path, host, tool o prefisso argv?
policy { … }Su ogni consume di capQuesto dominio è permesso in questo file, anche con un token?

Non sono lo stesso meccanismo. Una funzione pura non può chiamare cap.run. Un token non sblocca un path che la policy deny. Una policy non sostituisce un token — le API di consume rifiutano ancora stringhe e dict contraffatti. How-to dei token: 12.6.

approve non è lo statement approval dei workflow. Gli approval di workflow mettono in pausa un'istanza per un umano (capitolo 22). Il approve della policy è un flag env o un callback dell'host sul consume dei cap. Non aspettarti un dialog del Desktop IDE da policy { shell: approve }.

23.7 AgentError

Quando un prompt o un tool fallisce, le API più vecchie ti danno una stringa error. Le stringhe sono facili da stampare e difficili da usare in match. AgentError è un sum type built-in — una ragione taggata con campi — pre-registrato così non lo dichiari tu:

AgentError = Refused(reason) | Unparsable(raw, attempts) | SchemaMismatch(schema, error)
           | BudgetExceeded(kind, limit) | ToolDenied(tool, reason) | Timeout(ms)
           | Upstream(status, body)
VarianteSignificato tipico
Refused(reason)Il modello o l'host ha rifiutato la richiesta.
Unparsable(raw, attempts)Il completamento non era JSON usabile dopo i tentativi di repair.
SchemaMismatch(schema, error)Il JSON ha parsato ma non coincide con lo schema dichiarato.
BudgetExceeded(kind, limit)Il budget di token, tool o costo è finito.
ToolDenied(tool, reason)La policy o l'host ha rifiutato un tool / consume di cap.
Timeout(ms)Uno scope within o una deadline è scaduto.
Upstream(status, body)Un peer fallito (status HTTP, o uno slot fallito di all(…)).

Le stringhe { ok, error } esistenti restano. I throw restano throw — la scadenza di un within solleva ancora; non diventa un oggetto risultato silenzioso. I siti che già tornano un oggetto risultato attaccano anche agentError come variante. Mismatch di validate → SchemaMismatch.

schema Card { name: string; }
var r = validate("Card", dict { "email": "x" });
print(r.ok);
schema Card { name: string; }
var r = validate("Card", dict { "email": "x" });
print(str.indexOf(string(r.agentError), "SchemaMismatch") >= 0);

Leggi r.agentError per la variante taggata. Controllare solo la stringa error resta valido e continua a perdere il tag — non distingui SchemaMismatch da Timeout leggendo testo inglese. Vedi anche 4. Tipi di dati per match sui sum type.

23.8 Stream e for await

stream(value, schema?) trasforma un valore in un array di chunk così una UI può aggiornarsi man mano che arriva il testo. Ogni chunk è { text }, oppure un oggetto parziale schema-aware se passi un nome di schema registrato. for await (var x in expr) itera quella collezione.

Oggi il builtin materializza prima l'array; l'emit C# è un foreach sopra. Puoi comunque scrivere il loop che una UI streaming terrà quando esisteranno i token live. Non ti serve un LLM per imparare la sintassi: passare una stringa la spezzetta offline.

var n = 0;
for await (var chunk in stream("hello world from malda")) {
    n = n + 1;
}
print(n > 0);

Il parser incrementale dei prefissi JSON chiude oggetti/array parziali e produce il prefisso più grande che valida — così uno stream schema-aware può mostrare { "name": "Ad" } prima che arrivi la virgoletta di chiusura. LlamaCpp non ha uno stream di token live — i chunk sono ritagliati dal testo finito (il gap noto in cima al capitolo).

for await non è await prompt. await extract(...) chiama un modello e aspetta un risultato. for await cammina su una collezione che stream ha già prodotto. Puoi usare for await senza API key.

23.9 Sink grounded

Una risposta retrieval-augmented dovrebbe ricordare da dove viene. grounded.wrap(value, citations?) attacca metadata di citazione sul valore runtime — un post-it, non un nuovo kind per match. Continui a fare print del testo; puoi anche leggere .citations.

Interpolazione e str.* uniscono gli insiemi di citazioni. Mischiare testo grounded e ungrounded marca il risultato come parziale (alcuni pezzi hanno fonti, altri no).

var g = grounded.wrap("Ada", [{ "source": "wiki", "id": "1" }]);
var s = $"Hello {g}";
print(s.citations.length >= 1);

Passo passo: g è { value, citations, sourced }. Dentro $"Hello {g}" il wrapper si interpola come il suo value "Ada" e la stringa risultante tiene la citazione wiki. Non c'è un alias flat grounded() né una keyword Grounded. GraphMemory può tornare lo stesso wrapper da memory.ask / query(..., { grounded: true }) — vedi 19.3.15.

@requiresCitations su una funzione (e sui sink marcati come io.writeFile / risposta HTTP) dà errore quando un argomento stringa non ha citazioni. Usalo sull'ultimo hop prima di una risposta visibile all'utente o di una write su file, così un'allucinazione ungrounded non può uscire. match / validate non vedono un tipo nuovo — le citazioni viaggiano come dati.

Errore comune. Trattare i hit di memory.query(...) come se match potesse vedere le citazioni. Query torna un array di nodi. La provenienza resta a lato finché non fai wrap (o usi gli helper ASK sopra).

23.10 Ciclo check

malda check è il correttore ortografico della toolchain: diagnostica e non esegue. Usalo in un loop di agente o prima di lanciare un file sorgente. --fix poi applica una lista breve di edit meccanici — quelli non ambigui, non “riscrivi il mio programma”.

malda check app.malda --json
malda check app.malda --fix
malda prompts --diff .malda/evals.json
Cosa riscrive --fixIn
Alias flat della stdlib (print, sqrt, …)Chiamate namespaced (io.print, math.sqrt)
"total: {n}" (stringa plain, niente interpolazione)$"total: {n}"
items.length()items.length

Le diagnostiche --json possono includere suggestedFix (did-you-mean). Non ogni gotcha è auto-fixed — se lo strumento non è sicuro, avvisa soltanto. Gli alias flat e parseJson restano fino a un MAJOR 2.0 dedicato; --fix / gotcha sono la preparazione.

Sorgenti diagnostiche che vedrai nel JSON:

  • malda-gotcha — loop EOF di io.input, AnsiConsole.markup senza newline, validate inutilizzato, arr.append, omografo parseJson, borderStyle sconosciuto.
  • malda-tools — @Tool / @MCPTool senza type hint e senza argomento schema.
  • malda-agents — topologia statica del team (solo grafi / plan letterali).

L'opzionale @version("2026-09-01") su un prompt è un pin informativo. malda prompts --diff confronta gli hash dei prompt fra file di baseline eval così vedi che il template è cambiato anche quando l'eval continua a passare.

23.11 Un primo percorso nel capitolo

Se stai scrivendo il primo programma agentico, fai questi passi in ordine. Ogni passo resta offline finché non scegli altrimenti.

  1. Scrivi uno schema e un prompt (capitolo 10). Chiama evalPrompt con un dict fixture. Conferma checked.ok.
  2. Sposta quel check in una suite / case e lancia malda eval.
  3. Stampa trace.journal() così vedi l'evento prompt.
  4. Se il programma usa tool, aggiungi una policy che fa deny di shell (e readOnly sulla cartella di lavoro). Minta i token come in 12.6.
  5. Avvolgi il lavoro lento in within (30s) { … }.
  6. Quando finalmente fai await di un modello live, registra una cassetta e riascoltala con MALDA_REPLAY_STRICT=1.
  7. Prima di rilasciare il file, lancia malda check --json (e --fix se gli edit meccanici ti sembrano giusti).

Quel percorso usa ogni costrutto di questo capitolo tranne streaming e citazioni grounded, che aggiungi quando la UI o il progetto RAG li chiede.
