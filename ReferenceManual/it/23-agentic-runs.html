23. Esecuzioni agentiche

Questo capitolo è la superficie del linguaggio per verificare e delimitare i programmi agentici: suite di eval, cassette LLM, journal di run, scope di cancellazione, context di conversazione dichiarato, policy di capability a livello di file, AgentError tipizzato, streaming, sink grounded e il ciclo check/fix. Interprete e transpile C# coincidono sugli esempi offline. JavaScript è solo host (n/a).

suite, context, policy e within sono parole contestuali, non keyword riservate. var context = 1; continua a parsare. case è già una keyword (riusata per i case di suite vs match). expect e stream sono builtin. I flag CLI di questi comandi sono in 2. Strumenti e toolchain.

Gap noti (non inventare un workaround nella documentazione):
  • Examples/Prompts/prompt_tools_then_structured.malda interpreta offline; il costrutto C# oggi lancia NullReferenceException. La riga ship resta n/a.
  • llama.cpp / LLamaSharp in-process: stream() è bufferizzato (chunk dal testo finale), non token live.
  • policy { shell: approve } non è una UI di approval dei workflow. Auto-approva solo con MALDA_POLICY_APPROVE=1 o se un ApprovalCallback dell'host torna true; altrimenti deny.

23.1 Suite di eval

Una suite è un gruppo nominato di case di eval. malda run / l'interpretazione ordinaria salta le suite (come property). Si eseguono con malda eval. Non è malda test, che scopre le dichiarazioni property e i file *.test.malda — vedi 35. Property testing.

Lookahead dopo case: case "title" { è un case di suite; case Pattern: è un braccio di match.

schema Card {
    name: string;
}

prompt extract(raw) -> Card {
    user: raw;
}

suite "extract" {
    case "offline shape" {
        var checked = evalPrompt(extract("x"), dict { "name": "Ada" });
        expect(checked.ok);
    }
}

print("ok");

expect(cond) lancia come assert quando la condizione è falsa. Un expect fallito fallisce quel sample. validate continua a tornare { ok, error } e non lancia sul mismatch.

malda eval Examples/Prompts/eval_suite_offline.malda
malda eval path.malda --baseline .malda/evals.json
malda eval path.malda --baseline .malda/evals.json --update-baseline
  • @samples(N) — sotto MALDA_REPLAY, replay di N varianti registrate; senza replay, N sample live. N <= 1 gira una volta.
  • @threshold(0.9) — exit non-zero se il pass rate del case è sotto la soglia.
  • @judge(prompt gradeHelpfulness) — dopo un body che passa, valuta l'espressione judge (un prompt viene chiamato con il titolo del case). Un oggetto risultato con ok: false fallisce il sample.
  • Il confronto con una baseline esistente fallisce anche il processo quando il pass rate di un case cala.

Stesso file: Examples/Prompts/eval_suite_offline.malda. Snippet agent: docs/llm/few-shot/43_eval_suite.malda.

23.2 Cassette

Ogni path LLM Chat (HTTP, GGUF, client bridge) passa da un unico gate record/replay. Le cassette sono JSONL. I secret (Authorization, API key, stringhe con forma da secret) vengono redatti in record.

MALDA_RECORD=tests/cassettes/name.jsonl   malda Examples/path.malda
MALDA_REPLAY=tests/cassettes/name.jsonl   malda Examples/path.malda
MALDA_REPLAY_STRICT=1                    malda Examples/path.malda

La chiave della cassetta è hash del prompt + args canonici + model + mode (A/B/C) + hash dello schema. Un miss in replay scrive cassette_miss nel journal. Senza MALDA_REPLAY_STRICT=1 l'host avvisa e cade su una chiamata live. In strict mode lancia. Come registrare: tests/cassettes/README.md.

Examples/Agents/agent_governance_golden.malda è una pair interpret/transpile offline (senza cassetta). Examples/RalphWiggum/RalphWiggum.malda resta n/a (too-large).

23.3 Journal di run

Un journal in-process raccoglie eventi di prompt, tool, cap, hop e step di workflow. SQLite dei workflow resta lo store di durabilità; gli step riusciti sono anche specchiati qui così trace.journal() e gli eventi di workflow condividono un substrato.

schema Card {
    name: string;
}

prompt extract(raw) -> Card {
    user: raw;
}

var checked = evalPrompt(extract("Ada"), dict { "name": "Ada" });
var events = trace.journal();
print(events.length > 0);

Ogni evento è un oggetto con ts, span, kind (prompt / tool / cap / hop / step), name, opzionali promptHash / model / tokens / cost / ms / repairs / error, e ok.

  • trace.span("name", fn) — nidifica gli eventi sotto quel nome di span.
  • trace.lastUsage() — ultimo oggetto token/cost/ms registrato, oppure null.
  • .usage su un risultato di prompt è metadata. Una chiave propria dell'oggetto chiamata usage (campo schema) vince.

Export: MALDA_TRACE=jsonl|otlp più opzionale MALDA_TRACE_FILE. Non è il CLI malda trace esistente, che continua a leggere i file di sessione .malda-trace.jsonl. Stesso file: Examples/Prompts/run_journal_offline.malda.

23.4 Scope within

L'istruzione within (30s) { … } è uno scope di cancel a orologio da parete. Le unità sono un numero più ms, s o m (convertite in millisecondi). L'opzionale budget(tokens: N, tools: N, cost: N?) spinge un budget di risorse nidificato come @budget.

Il decoratore @within(ms) resta la deadline per funzione / think. Non è un'istruzione e accetta solo millisecondi.

within (10ms) {
    sleep(50);
}

print("should-not-print");

Alla scadenza il runtime scrive un timeout nel journal e lancia Timeout: exceeded within (…ms). La cancellazione arriva a LLM Chat e al consume dei cap. Stesso file: Examples/Prompts/within_sleep.malda (interpret e C# falliscono entrambi — pair sull'identità dell'errore, non sullo stdout).

  • race(tasks…) — primo ramo completato.
  • firstOk(tasks…) — primo ramo che non è una variante Timeout.
  • all(tasks…) aspetta ogni ramo. Un ramo fallito diventa uno slot AgentError Upstream; la chiamata non rilancia il primo errore.
  • cancelWorkflow(id) mette l'istanza in cancelled; il body interroga quello status fra le istruzioni.

23.5 context dichiarato

Una dichiarazione context Name { … } è un mini-DSL simile a uno schema. new Name() costruisce un oggetto journaled con .add e .turns.

context Session {
    budget: 800 tokens;
    pin: systemFacts;
    retain: last 2;
    evict: oldest;
}

var s = new Session();
s.add("user", "hi");
s.add("user", "there");
print(s.turns.length >= 1);
  • budget: N tokens — memorizzato sull'istanza (pin informativo).
  • pin: name, … — quei turn restano.
  • retain: last N — finestra dei turn.
  • evict: oldest | lowestScore | none.
  • compact: prompt summarize — prompt nominato opzionale; la compaction è una chiamata modello registrata (chiave cassetta) poi evict.

WF1006: compaction / mutazione del context dentro un body workflow deve stare in uno step. Callee importati o sconosciuti restano Info, come WF1005. Vedi 22. Workflow durevoli.

23.6 policy di confine del programma

Una policy { … } a livello di file è applicata sul consume dei cap indipendentemente da quali tool l'host ha registrato. La violazione scrive un evento cap nel journal e lancia ToolDenied: ….

policy {
    fs:    readOnly under "./work";
    net:   allow "api.example.com", "*.internal";
    shell: deny;
    mcp:   allow "local";
}
  • deny — rifiuta sempre quel dominio.
  • allow / readOnly — pattern path/host opzionali; readOnly rifiuta anche le write.
  • approve — richiede MALDA_POLICY_APPROVE=1 (o true) oppure un ApprovalCallback dell'host. Non c'è ancora un prompt interattivo in stile workflow.

@effects("pure") è ancora un check statico (i namespace IO includono cap). La policy è la deny list a runtime. Non sono lo stesso meccanismo.

23.7 AgentError

Un sum type built-in, pre-registrato:

AgentError = Refused(reason) | Unparsable(raw, attempts) | SchemaMismatch(schema, error)
           | BudgetExceeded(kind, limit) | ToolDenied(tool, reason) | Timeout(ms)
           | Upstream(status, body)

Le stringhe { ok, error } esistenti restano. I throw restano throw. I siti che già tornano un oggetto risultato attaccano anche agentError come variante. Mismatch di validate → SchemaMismatch.

schema Card { name: string; }
var r = validate("Card", dict { "email": "x" });
print(r.ok);

Leggi r.agentError per la variante taggata. Controllare solo la stringa error resta valido e continua a perdere il tag.

23.8 Stream e for await

stream(value, schema?) produce un array di chunk { text }, oppure oggetti parziali schema-aware se si passa un nome di schema registrato. for await (var x in expr) itera quella collezione (oggi il builtin materializza l'array; l'emit C# è foreach su di essa).

var n = 0;
for await (var chunk in stream("hello world from malda")) {
    n = n + 1;
}
print(n > 0);

Il parser incrementale di prefissi JSON chiude oggetti/array parziali e produce il prefisso più grande che valida. LlamaCpp non ha uno stream di token live — i chunk sono ritagliati dal testo finito.

23.9 Sink grounded

grounded.wrap(value, citations?) attacca metadata di citation sul valore runtime (non un nuovo kind di match). Interpolazione e str.* uniscono i set di citation. Mescolare testo grounded e ungrounded marca il risultato come parziale.

var g = grounded.wrap("Ada", [{ "source": "wiki", "id": "1" }]);
var s = $"Hello {g}";
print(s.citations.length >= 1);

@requiresCitations su una funzione (e sink marcati come io.writeFile / risposta HTTP) segnala errore quando un argomento stringa non ha citation. match / validate non vedono un tipo nuovo.

23.10 Ciclo check

malda check resta solo diagnostica. --fix applica edit meccanici: alias flat della stdlib → chiamate namespaced, "total: {n}" → $"…", items.length() → items.length. Le diagnostiche --json possono includere suggestedFix (did-you-mean). Non ogni gotcha è auto-fixato.

malda check app.malda --json
malda check app.malda --fix
malda prompts --diff .malda/evals.json

Sorgenti diagnostiche:

  • malda-gotcha — loop EOF di io.input, AnsiConsole.markup senza newline, validate inutilizzato, arr.append, omografo parseJson, borderStyle sconosciuto.
  • malda-tools — @Tool / @MCPTool senza type hint e senza argomento schema.
  • malda-agents — topologia statica del team (solo grafi / plan letterali).

L'opzionale @version("2026-09-01") su un prompt è un pin informativo. malda prompts --diff confronta gli hash dei prompt fra file di baseline eval. Gli alias flat e parseJson restano fino a un MAJOR 2.0 dedicato; --fix / gotcha sono la preparazione.
