28. REST API Server

MALDA includes native support for JSON-first REST APIs. Decorate functions with HTTP methods, then host them on RestServer (standalone) or mount that server on HttpServer for a single-port full-stack app.

Start here: This chapter is the API-first reference. Page hosting, @PAGE, HTTPS, static files, multipart uploads, and SSE live in 26. HttpServer & HTML UI Generation. Calling APIs from MALDA is 29. REST Web Client. JWT, CSRF, and password helpers are in 13. Built-in Functions.

28.2 Decorator Syntax

Functions decorated with an HTTP method become REST endpoints when a RestServer starts (or is mounted):

@GET("/api/users")
function getUsers() {
    return parseJSON("[{\"id\": 1, \"name\": \"Alice\"}]");
}

@POST("/api/users")
function createUser(body) {
    var jsonStr = "{\"id\": 3, \"name\": \"" + body.name + "\"}";
    return parseJSON(jsonStr);
}

28.2.1 Supported HTTP Methods

  • @GET(path) - Handle GET requests. HEAD matches the same route; the body is omitted.
  • @POST(path) - Handle POST requests
  • @PUT(path) - Handle PUT requests
  • @DELETE(path) - Handle DELETE requests
  • @PATCH(path) - Handle PATCH requests
  • @OPTIONS(path) - Handle OPTIONS requests (CORS preflight is handled separately when CORS is enabled)

Duplicate method+path pairs throw at startup. Use getRoutes() to inspect the registered table.

28.2.2 Route Metadata Decorators

Optional metadata decorators are applied before the route is registered. Prefixes compose as group + version + path.

  • @RouteGroup(prefix) / @Group(prefix) / @Prefix(prefix) - prepend a group prefix
  • @Version(version) / @ApiVersion(version) - prepend a version segment
  • @Use("middlewareName") / @Middleware("middlewareName") - route-level middleware by function name (a string, not an inline function)
  • @Validate(schema) - request validation schema (object or JSON string)
@RouteGroup("/api")
@Version("v1")
@Use("requireAuth")
@GET("/users/{id}")
function getUserById(id, req, res) {
    return res.json(parseJSON("{\"id\":\"" + id + "\"}"));
}

28.3 RestServer Class

28.3.1 Constructor

var server = new RestServer(port);
// OR
var server = new RestServer(port, host);  // host: "localhost" or "0.0.0.0"
// OR
var api = new RestServer();               // port 0: deferred / mounted

port must be 0 (deferred/mounted) or an integer in 1-65535. Privileged ports (1-1023) are allowed; binding may still require elevated permissions or OS URL reservations. Host defaults to localhost. Pass 0.0.0.0 to listen on all interfaces. Unlike HttpServer, there is no setHost method and no MALDA_HTTP_HOST override.

28.3.4 What RestServer does not host

Standalone RestServer is API-only. These belong on HttpServer (chapter 26): HTTPS / enableHttps, setHost / MALDA_HTTP_HOST, static files, @PAGE / @AIPAGE, multipart/form-data uploads, and SSE ({"sse": true}). The shared pieces are req / res / req.auth / req.session, CSRF, rate limits, and route metadata.

28.4 Request Pipeline

Every request runs this order. Knowing it matters for auth keys, CSRF, and validation:

  1. Resolve correlation ID: honor inbound X-Correlation-ID or generate one; echo it on the response
  2. CORS preflight (OPTIONS) when CORS is enabled, then CORS headers on the real request
  3. Swagger static paths when enabled
  4. Route match; no match → 404 standard envelope
  5. Parse body for POST / PUT / PATCH
  6. CSRF (before any application middleware)
  7. Global middleware (server.use)
  8. Route middleware (@Use / @Middleware)
  9. Rate limit (after middleware, so verifiedSub* sees req.auth)
  10. @Validate schema
  11. Parameter binding and handler
  12. Serialize or commit the response

Interpreted handlers run on an isolated interpreter per request. In interpret mode, assigning req.tenant = "acme" in middleware is visible to later middleware and the handler on that request only.

28.5 Parameter Binding

28.5.1 Path parameters

Placeholders in the route pattern bind by name:

@GET("/api/users/{id}")
function getUserById(id) {
    var jsonStr = "{\"id\": \"" + id + "\", \"name\": \"Alice\"}";
    return parseJSON(jsonStr);
}

28.5.2 Query parameters

Unmatched parameter names bind from the query string:

@GET("/api/users")
function getUsers(limit, offset) {
    // 'limit' and 'offset' extracted from ?limit=10&offset=0
    var jsonStr = "{\"users\": [], \"limit\": " + limit + "}";
    return parseJSON(jsonStr);
}

28.5.3 Request body

A parameter named body receives the parsed payload. Content types:

  • application/json → object / array (invalid JSON falls back to the raw string)
  • application/x-www-form-urlencoded → object of string fields
  • anything else → raw string

RestServer does not parse multipart/form-data. Use HttpServer for file uploads.

@POST("/api/users")
function createUser(body) {
    var name = body.name;
    var jsonStr = "{\"id\": 1, \"name\": \"" + name + "\"}";
    return parseJSON(jsonStr);
}

28.5.4 Special parameter names

These names always bind, in both name-based and decorator modes:

ParameterBinds to
req / requestRequest context
res / responseResponse context
params / pathParamsPath-parameter object
query / queryParamsQuery-parameter object
headersRequest headers
cookiesRequest cookies
bodyParsed body (name-based mode)

28.5.5 Decorator binding

Optional renaming. If any parameter has a decorator, undecorated parameters bind null (special names above still bind):

@PUT("/api/users/{id}/posts/{postId}")
function updatePost(@PathParam("id") userId, @PathParam("postId") postId, 
                    @QueryParam("limit") maxResults, @Body() updateData) {
    // userId = path param {id}
    // postId = path param {postId}
    // maxResults = query param ?limit=10
    // updateData = request body
}

In transpile mode the compiler registers routes with paramDecorators = null, so @PathParam / @QueryParam / @Body renaming works in the interpreter only. Prefer matching parameter names to path/query/body when you compile.

28.6.2 req.auth

Prefer req.auth.authenticateBearerJwt(secret) (APIs) or authenticateCookieJwt(cookieName, jwtSecret, cookieSecret?) (browser sessions). Both verify the JWT, populate claims/roles/permissions, and throw a standardized 401 on failure. Create tokens with createJwt (chapter 13).

function requireAuth(req, res, next) {
    req.auth.authenticateBearerJwt("my-jwt-secret");
    next();
}

@GET("/api/admin/stats")
function adminStats(req) {
    req.auth.requireRole("admin");
    return {
        "users": 2
    };
}

var server = new RestServer(8080);
server.use(requireAuth, {
    "except": ["/api/health", "/api/login"]
});
server.start();

Skip public paths with use(middleware, { "except": [...] }). Exact paths and trailing * prefixes are supported. Ingress aliases X-Malda-Auth-Verified / X-Malda-Auth-Sub (and legacy X-Auth-* / X-Verified-Sub) can pre-mark a subject; application middleware should still call authenticate* so roles and claims are present.

28.7 Response Handling

28.7.1 Return shapes

  • Plain object / array → JSON 200
  • Plain string → text/plain 200
  • { "status": 201, "data": ... } → HTTP status from status; that field is stripped from the JSON body
  • Standard error object {status, error, message} (see 28.11) → that status, body unchanged
  • res.status(...).json(...) (or other send helpers) → already committed; the return value is ignored
@POST("/api/users")
function createUser(body) {
    var jsonStr = "{\"status\": 201, \"data\": {\"id\": 1, \"name\": \"" + body.name + "\"}}";
    return parseJSON(jsonStr);  // Returns 201 Created
}
@GET("/api/users/{id}")
function getUser(req, res) {
    var id = req.params.id;
    return res.status(200).json(parseJSON("{\"id\": \"" + id + "\"}"));
}

28.7.2 Response helper API

MemberNotes
status(code)Set status; chainable
json / text / html / redirect / send / sendBase64 / fragmentSend and close immediately
header(name, value), setContentType(type)Headers before send
cookie(name, value, options?), clearCookie(name, options?)Defaults: HttpOnly=true, Secure=true, SameSite=Lax, Path=/. Options: domain, maxAge, sameSite, httpOnly, secure, path
flush()Send whatever is already committed (including status-only)
statusCode, contentType / type, headers, bodyReadable snapshot
committed / sent / isCommitted, flushed / isFlushedSend state

res.send(value) UTF-8-encodes a string body. Use res.sendBase64(b64) for binary payloads (PDF, DOCX, and similar): it decodes the base64 string and writes those bytes. Invalid base64 throws.

After a send helper, the handler may keep running (background work). Headers and cookies set after send throw response already sent. res.fragment(targetId, html) is the early-send form of componentFragment(targetId, html): same X-Malda-Fragment headers, but the client receives the fragment before the handler returns.

28.8 Middleware

Use server.use(...) for global middleware. The contract is (req, res, next). Call next() to continue; omitting it short-circuits. Route-level @Use("name") runs after global middleware and before validation + the handler. Transpiled apps should pass the function name as a string: server.use("requireAuth").

function logRequest(req, res, next) {
    print(req.method + " " + req.path);
    next();
}

var server = new RestServer(8080);
server.use(logRequest);
server.start();

28.9 CSRF, Rate Limiting, and Trusted Proxy

var server = new RestServer(8080);
server.enableCsrf("my-csrf-secret");                 // cookie: csrf_token, header: X-CSRF-Token
server.setRateLimit(120, 60, "verifiedSubOrIp");     // after auth middleware; prefer subject when verified
server.setRateLimitHeaders(true, true);              // add X-RateLimit-* + Retry-After headers
server.configureTrustedProxy(true, "X-Forwarded-For", 0); // trust first forwarded hop
server.use(requireAuth, { "except": ["/api/health", "/metrics"] });
server.start();

CSRF runs before middleware. Safe methods (GET/HEAD/OPTIONS) issue or refresh the CSRF cookie when missing or invalid. State-changing methods (POST/PUT/PATCH/DELETE) require a matching cookie plus request token from X-CSRF-Token, body.csrfToken, or body._csrf. Pair this with generateCsrfToken / csrfField from chapter 13 for browser clients.

Rate limiting runs after global and route middleware. verifiedSub* strategies key on the subject set by authenticateBearerJwt / authenticateCookieJwt; otherwise they fall back to IP/token. user keys on the X-User-Id header. Proxy headers are ignored until configureTrustedProxy(...) is enabled.

CSRF, auth, and rate-limit failures use the standard error envelope and include the correlation ID.

28.10 Validation

@Validate(...) checks path, query, and body before the handler. Invalid requests return HTTP 400 with field-level details and do not run handler logic. Schema values may be a JSON string or an object. Rules are a pipe DSL (int|required|min=1) or an object {type, required, min, max, minLength, maxLength, pattern}.

@GET("/search/{id}")
@Validate("{\"path\":{\"id\":\"int|required|min=1\"},\"query\":{\"q\":\"string|required|minLength=2\"}}")
function search(id, q) {
    return parseJSON("{\"ok\": true}");
}

For checks that depend on loaded data, call req.requireValid(schema) or req.validate(schema) inside the handler. Validation details items are {location, field, message}. When Swagger is enabled, @Validate metadata is reflected in OpenAPI parameter and request-body schemas.

28.11 Error Handling

Framework failures (404, CSRF, auth, rate limit, @Validate / req.requireValid, uncaught handler errors) use one JSON contract:

{
  "status": 401,
  "error": "InvalidToken",
  "message": "Invalid token signature.",
  "correlationId": "...",
  "details": [ ... ] // optional, present for validation errors
}
  • Response header: X-Correlation-ID (honors an inbound value)
  • Payload field: correlationId
  • Validation details: array of {location, field, message}
  • Set MALDA_WEB_DEBUG_ERRORS=1 (or true) to add a diagnostics object on 500s

A route miss is {"status": 404, "error": "NotFound", ...}. Uncaught throw of a plain object is not a custom HTTP status: it becomes 500 InternalServerError. To send a structured client error, return the standard envelope or use res.status(code).json(...):

@GET("/api/users/{id}")
function getUserById(id, res) {
    if (!userExists(id)) {
        return {
            "status": 404,
            "error": "NotFound",
            "message": "User not found"
        };
    }
    return res.json({
        "id": id
    });
}

req.auth.requireRole, requirePermission, requireVerified, and req.requireValid already throw that envelope.

28.12 CORS and Swagger/OpenAPI

var server = new RestServer(8080);
server.enableCORS(true);
server.setCORSOrigin("*");
server.setCORSMethods(["GET", "POST", "OPTIONS"]);
server.setCORSHeaders(["Content-Type", "Authorization"]);
server.enableSwagger(true);
server.start();

// OpenAPI JSON: /swagger.json, /openapi.json, /swagger/openapi.json

With Swagger enabled, GET those three paths (same document). Validation constraints from @Validate appear in the generated schemas.

28.13 Mounting on HttpServer

For a single listener that serves API routes first, then pages/components/static files, construct a deferred RestServer and mount it. Do not give the API its own port, and do not start() it as a standalone listener before mount.

var api = new RestServer();
var web = new HttpServer(8080);

function requireAuth(req, res, next) {
    req.auth.authenticateBearerJwt(jwtSecret);
    next();
}

@GET("/api/health")
function health() {
    return {
        "status": "ok"
    };
}

web.mount(api);
web.enableSession(sessionSecret);
api.enableCsrf(csrfSecret);
api.setRateLimit(200, 60, "verifiedSubOrIp");
api.use(requireAuth, {
    "except": ["/api/health"]
});
web.start();
  • Configure CSRF, rate limits, and API middleware on the RestServer instance
  • Session cookies often live on HttpServer (pages + API share the listener)
  • Mounted api.start() does not bind a port; it only marks the API as running with the host
  • A RestServer that already has its own listener cannot be mounted
  • Canonical starter: malda new fullstack → Templates/fullstack/backend/app.malda

28.14 Interpret vs Transpile

  • Name-based binding, @RouteGroup / @Version / @Use / @Validate, and req/res work in both modes
  • @PathParam / @QueryParam / @Body renaming is interpret-only (see 28.5.5)
  • In transpile, @GET and @POST are also registered on HttpServer. A compiled process that constructs both servers can see the same GET/POST routes on each
  • Pass middleware to use as a function-name string in transpile: server.use("requireAuth", { "except": ["/api/health"] })
  • Route-level @Use always takes a function name string

28.15 Complete Example

function json(str) {
    return parseJSON(str);
}

@GET("/api/health")
function healthCheck() {
    return json("{\"status\": \"healthy\"}");
}

@GET("/api/users/{id}")
function getUserById(id) {
    var jsonStr = "{\"id\": \"" + id + "\", \"name\": \"Alice\"}";
    return json(jsonStr);
}

@POST("/api/users")
function createUser(body) {
    var jsonStr = "{\"status\": 201, \"data\": {\"id\": 3, \"name\": \"" + body.name + "\"}}";
    return json(jsonStr);
}

var server = new RestServer(8080);
server.start();

while (server.isRunning) {
    sleep(1000);
}
