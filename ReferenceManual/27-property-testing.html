33. Property Testing

MALDA supports language-level property declarations for deterministic, seed-based generative testing through malda test.

33.1 Declaring and Running Properties

property intIdentity(x) {
    return (x + 0) == x;
}

Run properties with deterministic replay metadata:

malda test --iterations 100 --seed 1337

33.2 Failure -> Shrunk Counterexample -> Regression Artifact

Use deterministic seeds for reproducible failures, then opt-in artifact generation to capture the canonical (shrunk) counterexample as a standalone regression file.

# Run property tests with deterministic replay metadata
malda test ./tests --iterations 100 --seed 1337

# Generate regression artifacts for failing properties
malda test ./tests --iterations 100 --seed 1337 --write-regression

# Optional custom output directory
malda test ./tests --write-regression --regression-dir ./artifacts/regressions

# Emit CI JSON consumed by IDE/Desktop "Create Regression" action
malda test ./tests --format ci --iterations 100 --seed 1337

Default artifact location is tests/regressions. Generated files are deterministic .spec.malda repro artifacts and MALDA prints each path with Generated regression: ....

IDE/Desktop Create Regression treats CI suggestions as untrusted: recommended paths are sanitized and clamped to the active workspace before writing files.

CI JSON includes property metadata fields for tooling integrations, including shrunkCounterexample, canGenerateRegression, and recommendedRegressionPath.

33.3 Running a Property Inside a Script

You can execute a declared property directly inside a MALDA script using runProperty(name, iterations?, seed?).

property stableIdentity(x) {
    return (x + 0) == x;
}

var result = runProperty("stableIdentity", 40, 1337);
print("Passed: " + string(result.passed));

runProperty(...) returns an object with these fields:

  • propertyName, passed, iterations, seed
  • failedTrial, error, counterexample, shrunkCounterexample

33.4 Capability Model

Properties can declare capability requirements and explicit backend targets using decorators:

@requires("core", "actors")
@targets("interpreter", "csharp", "js")
property actorSafetyInvariant(x) {
    return x == x;
}
  • @requires(...): Declares required capability tags for the property.
  • @targets(...): Declares the backend modes where the property is expected to run.

Supported capability module tags for @requires(...) are:

  • Interpreter: core, file-io, actors, workflows, dotnet-interop, host-interop
  • CSharp: core, file-io, actors, workflows, dotnet-interop, host-interop
  • JS: core, web-dom, game-canvas

If a property requires a capability not supported by a backend, that backend is reported as not applicable (not as a failure).

The capability matrix is the source of truth for backend eligibility across interpreter, csharp, and js.

33.5 JavaScript Limitations and Skip Semantics

JavaScript backend parity is capability-gated. If a property requires unsupported JS capabilities, MALDA reports the JS mode as not applicable with a reason. This does not count as a parity failure for supported backends.

For JS-eligible properties where a JS property harness is not enabled yet, MALDA reports JS as skipped with an explicit TODO-style reason instead of failing parity.
